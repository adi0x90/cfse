# PROPOSAL-CONTRACT-REPAIR

**Status:** DRAFT — implementation prepared for review; not a released specification.

**Created:** 2026-11-09

**Target:** Next major release, version to be assigned during release preparation.

## Summary

Align CFSE's schemas, normative prose and examples around a consistent static contract for lifecycle records, Exploration outcomes and invariant logic. Supply synthetic conformance vectors and a standalone public schema test suite.

## Motivation

The existing contract permits Scenario lists despite TR-2's exactly-one rule; requires lifecycle fields that artifact schemas reject; allows empty observations alongside confirmed verdicts; and treats response success as sufficient evidence in one chapter while rejecting that interpretation in another. An invalid Interaction ID also makes the complete Flow example fail its own schema.

The `logic` length constraint cannot distinguish a formal expression from nonsense. A separate semantic-validation obligation is needed, with clear reporting of checks that were not performed.

## Proposed normative changes

| Files or area | Change |
|---|---|
| `spec/artifacts/primary/exploration/` | Scalar Scenario reference; outcome-dependent observations and verdicts; direct-evidence and target-consistency requirements. |
| `spec/grammar/schemas/grammar.schema.yaml` | Shared lifecycle metadata constraints, nonblank text and consistent Verdict values. |
| Schemas and prose for Concept, Entry Point, Projection, Interaction, Flow, Scenario, Exploration, Finding, Trace, Invariant, Predicate and Generator | Accept shared lifecycle fields; require version and approval date for `ACTIVE`, and deprecation date for `DEPRECATED`. |
| `spec/artifacts/supporting/patch/` | Require every recorded rerun to report `HOLDS` before a Patch is `COMPLETE`. |
| `spec/grammar/03-formal-logic.md` and `04-field-types.md` | Specify parse, binding, signature and attribute checks; align grammar and examples; separate static checks from proof or temporal evaluation. |
| `spec/foundations/conformance.md` | Separate validation results and require unsupported checks to remain `not_checked`. |
| `spec/semantics/01-invariant-states.md` through `05-delta-interpretation.md` | Align lifecycle, traceability, verdicts and evidence rules with artifact schemas; remove the contradictory inline DeltaAnalysis schema. |
| Complete artifact examples | Add lifecycle metadata, correct the Flow Interaction ID and avoid status-code-only evidence claims. |
| `spec/changelog.md` | Record these requirements as unreleased breaking changes. |

Public schema identifiers remain under `https://cfse.ai/schemas/`. The existing `trigger.initial_interaction` field remains intact.

## Compatibility and migration

This is a breaking change under the repository's release policy. It can reject previously accepted records and changes the requirements for claiming confirmed outcomes. Keep it under `[Unreleased]` until a major release is prepared. The current `VERSION` is not changed by this proposal.

The [migration guide](../guides/migrations/contract-repair.md) explains each record transition. Migration must preserve evidence and approval history; missing facts cannot be generated by a validator.

## Validation and claim boundaries

The [test suite](../tests/README.md) checks all local schemas and references, complete artifact examples, public namespace/flow compatibility, and 42 synthetic schema expectations. Optional external-validator integration exercises semantic expectations in two serializations.

Public CI does not depend on a private repository and does not claim to perform semantic validation. Publishing a compatible semantic-validator implementation is a separate tooling decision. Static checks do not authenticate evidence, establish actual approval, evaluate temporal properties or prove security.

## Alternatives considered

1. **Fix only individual examples and descriptions.** Smaller change, but lifecycle and evidence contradictions remain executable in the schemas.
2. **Repair the coordinated core contract.** Recommended: the dependent schemas, prose and examples change together, with explicit migration requirements.
3. **Import a broader implementation and research workflow.** Larger scope than the public specification needs; introduces unrelated dependencies and release decisions.

## Review and release

Before opening a public PR, open the normative-change proposal issue required by [CONTRIBUTING.md](../CONTRIBUTING.md) and link this rationale. Maintainer acceptance and release preparation remain distinct from a passing test run. No version tag, release announcement or automated corpus migration is part of this proposal.
